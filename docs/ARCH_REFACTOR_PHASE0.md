# 架构改造阶段 0（冻结与基线）

> 状态：已落地（可执行）
>
> 目标：在不引入新功能的前提下，建立后续架构改造的稳定基线、执行边界与回滚点。

## 1) 冻结策略（Feature Freeze）

阶段 0 期间只允许以下改动：

- 架构重构（不改变游戏规则与交互语义）
- 测试补充与测试修复
- 文档与流程完善
- 明确的 bug 修复（需附复现与验证）

阶段 0 期间禁止：

- 新功能开发
- 游戏平衡性调整
- UI/文案功能性变更（非 bugfix）

---

## 2) 基线回归（必须通过）

### 2.1 最小测试全集

执行：

`python -m unittest discover -s tests -p "test_*_minimal.py"`

通过标准：

- 全部通过（当前基线为 94 项）
- 无新增 error/failure

### 2.2 关键交互冒烟（运行时）

执行目标：覆盖“进入对局 -> 渲染 -> 鼠标交互 -> 帮助覆盖层与资源加载”等高风险链路。

建议最小路径：

1. 启动对局并进入 `PLAYING`
2. 执行 `_render_gameplay()`
3. 模拟鼠标移动/左键/右键
4. 打开帮助覆盖层并触发规则图加载
5. 覆盖地图包围盒查询与折线绘制路径

通过标准：

- 运行期无异常中断
- 关键状态字段不出现缺失

---

## 3) 改造任务卡（阶段 0 模板）

后续每一项架构改造，都按下表记录：

| 字段       | 要求                 |
| ---------- | -------------------- |
| 任务名     | 清晰描述改造范围     |
| 影响文件   | 列出核心文件         |
| 行为等价性 | 明确“规则不变”检查点 |
| 回滚点     | 可回退到的提交/标签  |
| 验证项     | 最小测试 + 专项冒烟  |
| 结果       | 通过/失败与原因      |

---

## 4) 回滚策略

建议每一轮“可独立回退”的改造都满足：

- 单轮改动聚焦一个主题
- 对应测试在同一轮补齐
- 回归在同一轮完成

推荐实践：

- 以小批次提交（每批可独立回滚）
- 每批提交前后都运行基线命令
